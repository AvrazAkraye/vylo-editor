# R4 Whole-app regression and performance: requests

What review R4 found that is larger than a fix it may make (its lane: the scene hook in `motiondraw.ts`,
`motionscene.ts`, `MotionChecks.tsx`'s scheduling, lazy imports). In order of importance. The numbers and how they
were taken are in `docs/pro/review-regress.md`.

## 1. The preview freezes while a sound bed is rendered (motionsound.ts, package 04)

**Breach of PRO.md's "preview stays smooth".** `renderSoundBed` runs on the main thread in one piece. The effects
mix (`mixCues`) never yields, and the music path holds the thread for up to a few hundred milliseconds at a time.
Measured in the app's own WebKit, playing Big title at 60 Hz with the frame gaps recorded (scenario
`.test-build/qa/s22-soundhitch.ts`, two runs):

| Change while playing | Longest frame gap | Frames over 100 ms |
|---|---|---|
| nothing (baseline) | 19 ms | 0 |
| Sound: Off → Both | 248 / 264 ms | 2 / 2 |
| Level slider moved | 222 / 236 ms | 2 / 2 |
| Another mood | 948 / 316 ms | 2 / 2 |
| Both → Effects | 85 / 86 ms | 0 / 0 |

In isolation (`soundBlock` in `.test-build/r4/perf-pro.ts`, a 4 ms ticker beside the render): Effects for 10 s holds
the thread 121 ms with no break, for 30 s (stats) 349 ms; Music 10 s, longest hold 214 ms of a 649 ms render; Both
10 s, 144 ms of 570 ms. Words do not trigger it (they are not in `soundKey`), so typing is unaffected; the length,
a layer's timing, a mode, a mood or the level do, 250 ms after the change settles.

Ask: make the render cooperative: in `mixCues`, and in any long per-sample loop after the music (the loudness pass,
the fades), give the thread back every ~8 ms (`await new Promise((r) => setTimeout(r, 0))` between batches of cues
or blocks of samples), checking the abort signal at each break. The bed's bytes must not change (the export tests
pin them). A Worker is the cleaner end state for the effects but not for the music (WebKit has no
`OfflineAudioContext` in a worker).

## 2. The glitch transition's memory (motiontransition.ts, package 05)

Not a leak: over 2,000 frames of a four-scene graphic the web content process stays flat after the first loop. But
while a **glitch** plays at 1080p the web content process rises by about 150 to 250 MB (156 → 316 → 253 MB over
900 frames), where every other kind adds about 15 MB (fade, push, iris, pixelate, whip, zoom: 107 → 120–127 MB;
a cut 107 → 114 MB). The GPU process rises by 100–200 MB for any transition and falls back (148 → 170–339 MB,
not monotonic). `glitch` draws the scene picture up to 128 times per frame (slices) and re-tints the scratch canvas
twice; each changed canvas drawn onto the stage is a fresh snapshot in WebKit. Worth a look: fewer, wider slices,
or one tinted copy per step reused across frames of the same step (the slices change only twelve times per
transition, `GLITCH_STEPS`). Same result with document canvases instead of `OffscreenCanvas` (measured), so the
choice of canvas is not the cause.

## 3. The model's prompt doubled (motionai.ts / motiondirection.ts, package 10 and W2-3)

Not performance of the app, but cost and latency of every Make it and Ask: the plan prompt went from 8,997 to
17,886 characters (`all-s03a` scenario, `request1.systemChars`; the test's budget was raised from 9,500 to 27,231),
the edit prompt to about 20,115. That is roughly 2,000–2,500 more input tokens per request. If that was the
intent of the AI direction package, say so in its report; if not, the per-template lines (up to 502 characters
each, 33 templates) are where it went.

## 4. The test chain took 2.4 times as long (package 08 mostly)

Every step run on its own, summed: 31.1 s at the base, 75.4 s now, with `pro-templates-b.test.mjs` alone 16.6 s
(then `motionfuzz-templates` 5.6 s, `pro-audio` 4.9 s, `pro-sound` 4.1 s). `npm test` itself: 1 min 14 s wall.
The 528-combination sweeps are worth keeping; a lighter default with the full sweep behind an environment variable
would bring the chain back near its old time.

## 5. Smaller, for whoever touches the file next

- `MotionChecks.tsx` checks the graphic twice on open (once in `useState`, then again 250 ms later from the mount
  effect, for the same document) and again on every `loadingdone` of any face in the page. Each is 1–7 ms, so it is
  not a regression worth a change now; skipping the effect when `latest.current` is the document already checked
  would remove the second.
- The full window's stage is about 8% smaller than at the base (1047 × 589 → 960 × 540 at a 1500 × 950 window;
  the sidebar's canvas 28 px shorter) because the check row and the scene band are always there. Accepted by W2-1,
  noted for the interface review.
- Opening Motion costs about 15 ms more in the production bundle (61.5 → 76.5 ms, median of ten fresh starts) and
  a template about 7 ms more (22 → 29 ms: the first check runs before the chip shows). Within budget; the GIF
  writer (`motiongif.ts`, ~10 KB minified) could be an `import()` from `renderGif`, but it would save under a
  millisecond, so it was left.
