# Requests from S1 (final sample files)

S1 regenerated the export samples from the final `pro` build and checked them again (`docs/pro/samples.md`). The files
are right. One problem turned up in a file outside S1's lane. S1 changed no source file.

## 1. `motionsound.ts` (F3's cooperative render): in a hidden page every break waits about a second

**What happens.** F3 made the sound bed give the thread back every 8 ms (`Pace.breathe` → `nextTask`, which is
`setTimeout(resolve, 0)` in the page). WebKit throttles timers in a hidden page. In the off-screen test page
(`document.hidden` true, `visibilityState` "hidden"), once the chain of timers has run a few times, each
`setTimeout(0)` waits **about 1 s**. A bed of a few seconds or more needs dozens of breaks, so an export with sound takes
seconds or minutes longer in a hidden page. The bytes are unaffected: every film's loudness, peaks and sync measure as
before (`vylo-pro-samples-final/README.md`).

**Evidence** (macOS 26.2 WKWebView, the R2 harness host, off-screen and hidden; never the owner's app):

| measurement | R2's code (`2758ba7`, before F3) | final `pro` (`42a00b3`) |
|---|---|---|
| four-scene film, 12 s, Both, exported side by side twice in the same host | 3,187 ms, 3,117 ms | **14,117 ms, 16,574 ms** |
| the sample set (one run each): 30 s, ten scenes, blur, Both | 27,845 ms (R2's run) | **70,137 ms** |
| bar-chart race, 12 s, Music | 2,957 | **11,227** |
| level 100%, steps, 7 s, Both | 2,002 | 6,355 |
| Effects only, loop background, 8 s | 1,438 | 6,064 |
| title, 6 s, Effects / the same title with sound Off | 1,066 / 897 | 1,050 / 891 (unchanged) |
| bare `setTimeout(0)` × 40 in that page | | median **1,000 ms**, max 1,002, 29.5 s in all |
| one 12 s Both bed (04), every timer it set recorded | | **61.0 s**: 71 timers of 0 ms asked, median 989 ms waited, 57.1 s of the 61.0 |
| one 6 s Effects bed (01), the same | | 29.0 s: 29 timers, median 991 ms, 28.6 s waited |

The bed timings come from S1's `bedTime` probe (`docs/pro/samples/samples.ts`), run after the page had been hidden a
while. In the export runs the throttling had not yet fully set in, which is why those took 6 to 70 s rather than a
minute or more. Short films with few breaks (01, 02, 05, 06, 4 to 6 s) were not measurably slower.

**When the real app meets it.** Whenever its page is hidden while an export with sound runs. That can happen if the
window is minimised, on another Space, or fully covered, if WKWebView reports that as hidden (its default occlusion
behaviour; **not verified in the app**). R2 also noted that an export started by a chat call can finish in a hidden
page. With the window visible, F3's own numbers stand: every bed it measured rendered in under a second.

**Proposed fix** (whoever owns `motionsound.ts`). While the page is hidden there are no frames to make room for, so
the break need not wait for a timer. In `nextTask`, when `document.hidden` is true, resolve through a `MessageChannel`
message (F3 measured it: no wait; the 10 s Effects bed took 95–101 ms that way), or skip the break and only check
the signal. Keep `setTimeout(0)` while the page is visible, as F3 designed. A test could stub `document.hidden` and a
slow `setTimeout` and assert that a hidden render never waits on a timer. Worth one manual check in the real app: export
a 12 s graphic with Both sound, then minimise the window straight away, and compare the time with the window left open.
